# PRD.md 模板

`PRD.md` 是写给后续开发环节的 AI 看的需求文档：它要能只靠这份文件就知道做什么、不做什么、怎样算做成。所以每一条都要能追溯到用户的话，没说清的明确标「待确认」，而不是写一个看起来合理的猜测。

按下面的结构写，`{}` 处替换成实际内容。小节标题保持原样：后续的「回答问题」和「加新需求」要靠这些标题定位。

```markdown
# PRD —— {产品名}

| 项 | 内容 |
|---|---|
| 产品名 | {产品名} |
| 产品类型 | AI Agent |
| 当前版本 | V1 |
| 配套方案 | [方案.md](方案.md) |

## 版本演进记录

| 版本 | 日期 | 变更 | 来源 |
|---|---|---|---|
| V1 | {今天的日期 YYYY-MM-DD} | 初始需求 | 首次需求 |

## 1. 原始需求（逐字保留，不改写）

{用户确认过的草稿，原样贴进来，一个字都不改}

## 2. 需求拆解

| 维度 | 结论 | 状态 | 出处 |
|---|---|---|---|
| 目标 | {要完成什么、可量化的成功标准} | 明确 / 待确认 | {用户原话的引用；没有就留空} |
| 用户 | {谁在用、频率、同步还是异步} | | |
| 核心闭环 | {一次完整的「输入 → Agent 行为 → 交付物」} | | |
| 交付物 | {代码、文档、决策、操作，还是别的} | | |
| 边界 | {明确不能做什么} | | |
| 约束 | {时延、并发、合规、成本、可用模型} | | |

## 3. 功能需求

- **FR1**（V1）：{一条可验证的功能，写清输入、行为、输出}
- **FR2**（V1）：…

## 4. 边界与红线

- {绝对不能做的事，每条一行；来自用户原话或「待确认」}
- 出错时：{用户说过的出错处理；没说就写「待确认」}

## 5. 成功指标（可度量）

| 指标 | 目标值 | 怎么采集 |
|---|---|---|
| {例如：记账识别准确率} | {用户给的数值；没给写「待确认」} | {例如：每周抽查 20 条} |

## 6. 待确认问题与回答

（问题从 方案.md 的「待确认清单」搬来。用户的回答写在问题下方并注明日期；没回答的保留，不要删。）

1. {问题}
   - 回答（{日期}）：{用户的回答}

## 7. 待消化的新需求

（提出新需求时追加到这里；消化进上面各节后清空本节，并在版本记录里补一行「已消化」。）
```

## 写的时候注意

- **第 1 节逐字保留**：这是整个文档的「原始证据」。后面所有小节都从它推出来，开发环节的 AI 有疑问时会回来查它。
- **状态只有两种**：用户原话能直接支撑的写「明确」，其余一律「待确认」。推断出来的结论也要标「待确认」，并在结论里写清是推断。
- **不要自己定数值**：用户没给的阈值、次数、金额、时长、年龄，写成「（假设，待确认）」并放进第 6 节。
- **功能需求要能验证**：「好用」「智能」这类词不算功能需求；写成「用户发一句『买菜 35』，系统记一笔 35 元的『买菜』支出并回复确认」这种能判断做没做到的句子。
- **日期**用今天的真实日期。
