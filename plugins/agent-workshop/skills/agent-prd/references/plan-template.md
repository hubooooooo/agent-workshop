# 方案.md 模板（技术方案）

`方案.md` 回答「这个 Agent 该怎么搭」：选哪些机制、为什么、分几层、有哪些工具、怎么防出错。它和引擎生成的方案结构一致，开发环节（agent-builder 技能，或任何 AI 编程工具）直接按它动手。

推导分四步，每一步的产出是下一步的输入。组件、特征、七层、验收标准的定义都在 [components.md](components.md)。

## 第 1 步：需求拆解
把 PRD 第 2 节的六维表搬过来，再对照下面 8 个问题，把 PRD 没回答的写成**问用户的句子**，放进待确认清单：

1. 要达成什么？一句话说清产品目标，以及怎样算做成。
2. 给谁用？目标用户、使用频率、同步还是异步交互。
3. 一次完整交付长什么样？从用户输入到交付物的完整闭环。
4. 需要什么外部动作？必须调用的系统、API、数据源。
5. 领域知识在哪？模型必须知道的规则、文档、schema。
6. 什么绝对不能做？安全红线、数据边界、合规约束。
7. 失败怎么办？工具失败、模型幻觉、超时、越权时的降级策略。
8. 怎么算成功？可度量的指标（完成率、时延、成本、准确率）。

## 第 2 步：领域建模
把需求映射到 Harness 五要素（工具、知识、观察、行动、权限），每项 2 到 6 条。

## 第 3 步：组件选型
1. 运行 `select_components.py --features` 看 14 个特征问题，逐个判断 yes / no / later / unknown，每个配一句依据（引用用户原话最好）。判断标准见 components.md 第 3 节。
2. 把判断写成 JSON 交给脚本，拿到选型表。**脚本给出的选否不要改**：它是固定规则，保证同样的需求每次得到同样的选型。觉得结论不对，回去改特征判断和依据，再跑一次。
3. 判断为 unknown 的特征，把它的问题加进待确认清单。

## 第 4 步：架构设计
在已定的选型上写：七层架构、工具清单、系统提示词、上下文与记忆策略、安全与降级、可观测性、技术栈与部署、测试设计。

## 各部分的要求

**工具清单**：3 到 8 个工具。名称用英文 snake_case。每个工具都要能从五要素的「工具」和「行动」条目推出来。权限三选一：直接执行（无副作用、可撤销）、先问人（写入、发送、花钱、碰隐私）、禁止（红线）。调外部系统、知识库、第三方 API 的归 ⑤，读写需要持久化的数据的归 ⑥。

**系统提示词**：写成模型真能用的提示词，不是对提示词的描述。规则部分要把 PRD 第 4 节的红线落进去。

**安全与降级**：3 到 8 条「场景 → 处理方式」，必须覆盖四类：工具失败、模型幻觉、超时、越权。

**可观测性**：日志和指标各 2 到 5 条；轨迹一句话说明怎么记。

**技术栈与部署**：第一版的部署形态（单进程 / 服务 / 团队）、语言、模型来源，一条命令怎么启动，配置与密钥怎么外置（如 `.env`）。用户没指定技术栈时，选最简单能跑的方案，并在待确认清单里留一条技术备注让开发者确认。

**测试设计**：2 到 6 条，至少覆盖核心循环与工具分派的单元测试，以及权限与安全边界的测试（写清要测哪些拦截或红线）。

**不编造**：用户没给的具体数值（阈值、次数、年龄、时长、价格）不要自己定；需要时写成「（假设，待确认）」并放进待确认清单。

**待确认清单分两类**：用户能答的写成大白话问题放「需求问题」，只有工程师能判断的放「技术备注」。小白用户只需要看前一类。
