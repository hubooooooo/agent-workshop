# 交付前自查

引擎在生成方案后会让另一个模型做独立审稿。这里没有第二个模型，所以由你按同一套标准自查一遍。自查不能代替独立审稿，在 方案.md 的「自查结果」里如实写明「作者自查」，不要写成「审稿通过」。

逐条检查，发现问题就先改文档，改不了的（缺用户信息）写进待确认清单：

1. **无编造**：PRD 和方案里每一个关于用户、目标、核心闭环、边界、约束的陈述，都能在 PRD 第 1 节的原话里找到依据，或者已经标了「待确认」。挨个对一遍，这是最容易出错的地方。
2. **没有自定数值**：用户没给的阈值、次数、金额、时长都标了「（假设，待确认）」。
3. **选型和依据一致**：组件选型表是脚本原样输出的；每个特征的依据能对上用户原话；判为 unknown 的特征都进了待确认清单。
4. **工具和五要素一致**：每个工具都能对应到五要素里的某一条；先问人和禁止的工具，和 PRD 第 4 节的红线对得上。
5. **四类降级都覆盖**：工具失败、模型幻觉、超时、越权。
6. **六条验收标准都有对应设计**：可运行、可容错、可观测、可测试、可部署、可度量，每条都在方案里找得到具体做法。
7. **PRD 和方案一致**：两份文件的产品名、版本号、待确认问题对得上；方案里的待确认需求问题都已搬进 PRD 第 6 节。
8. **小白看得懂待确认清单**：「需求问题」里没有技术术语，用户读完就知道要回答什么。

自查结果写成两三句话的总体结论，再列出仍存在的问题（标高 / 中 / 低）。有高优先级问题时，结论写「方案仍是待修订草稿」，并告诉用户最该先回答哪几题。
