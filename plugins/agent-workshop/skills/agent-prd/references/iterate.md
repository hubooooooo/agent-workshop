# 交付之后：回答问题、加新需求

PRD 和方案不是一次写完的。第一版会留下待确认问题，用户回答、提新想法，文档一轮轮补全。规则和 Agent 工坊引擎的产品循环一致。

## 用户回答待确认问题

用户说「我来回答这些问题」，或者直接开始回答清单里的某题时：

1. **一题一题来**。把问题用大白话再说一遍，附两三个可选方向供参考（标 A / B / C），用户可以选一个或说自己的想法。用户说「帮我想想」时给方向和各自的利弊，但不要替他选。
2. 每得到一个回答，写进 PRD 第 6 节对应问题下方：`- 回答（YYYY-MM-DD）：…`，用户原话为准。
3. 回答影响到的小节一起更新：PRD 第 2～5 节（把对应的「待确认」改成「明确」，出处写「第 6 节回答」），以及方案里受影响的部分。
4. 回答改变了某个特征的判断（比如用户说「要每天早上自动推送」→ `scheduled` 从 unknown 变 yes），就重跑 `select_components.py`，更新选型表；选型变了，相应更新工具清单、架构图和安全策略。
5. 答完一轮重新自查（[self-check.md](self-check.md)），告诉用户还剩哪几题、选型有没有变化。

回答问题不升 PRD 版本：问题本来就在 V1 里，回答是在补全它。

## 用户提出新需求

用户说「加一个功能」「我又想到……」「能不能也支持……」时，这是新需求，要升版：

1. 把旧版存档：`PRD.md` 复制成同目录下的 `prd/V{n}.md`，`方案.md` 复制成 `prd/V{n}.方案.md`（存档已经存在就不要覆盖）。
2. 新需求用户只说了一句、不够具体时，最多追问一个问题（这个改动做到什么程度算好），然后整理成一段话，请用户确认。
3. 升版：PRD 表头「当前版本」改成 V{n+1}；版本演进记录加一行 `| V{n+1} | 日期 | 新需求摘要 | 新需求 |`；新需求原话追加到第 7 节，标题 `### V{n+1}（日期，待消化）`。
4. 消化新需求：把它合并进第 2～5 节，新增或改动的条目标注「V{n+1} 新增」/「V{n+1} 修改」；新问题进第 6 节。消化完清空第 7 节的这一块，版本记录这一行的「来源」补上「已消化」。
5. 重推方案：重新判断受影响的特征，重跑选型脚本，更新方案。上一版判断没被新需求影响的特征保持原判断，免得选型无故翻来覆去。
6. 在 方案.md 开头加一段「本版变化」：哪些组件的选型从什么变成什么，工具清单增删了什么。用户和开发环节都靠这一段知道要改哪里。

同一轮里重推失败或中途放弃（比如用户改主意）时，把 `prd/V{n}.md` 拷回 `PRD.md` 恢复原状，不要留下升了一半的版本。
