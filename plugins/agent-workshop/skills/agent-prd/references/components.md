## 1. 需求的六个维度

- `goal` 目标：产品要完成什么？可量化的成功标准是什么？
- `users` 用户：谁在用？人机比？同步还是异步？
- `core_loop` 核心闭环：一次完整的「输入 → Agent 行为 → 交付物」
- `deliverable` 交付物：代码、文档、决策、操作，还是别的？
- `boundaries` 边界：明确不能做什么？
- `constraints` 约束：时延、并发、合规、成本、可用模型

## 2. Harness 五要素

Agent = 模型 + Harness。Harness 由五个要素构成，方案的「领域建模」就是把需求映射到这五项：

- `tools` 工具：交付物需要什么外部动作（查询、写入、调用、发送）
- `knowledge` 知识：领域专长从哪来（文档、schema、业务规则）
- `observation` 观察：如何确认动作产生了预期效果（日志、diff、状态）
- `action` 行动：动作以什么形式执行（API、CLI、UI、消息）
- `permissions` 权限：哪些动作需要审批，哪些数据不能碰

每个要素写 2 到 6 条，每条一句话，具体到「什么系统 / 什么数据 / 什么动作」。需求里没有依据的不写，宁可少写。权限要素至少要有一条「默认拒绝」或「需要审批」的规则，除非用户明确说没有任何敏感操作。

## 3. 14 个特征（决定选哪些组件）

每个特征判断为 `yes` / `no` / `later` / `unknown`，再交给 `scripts/select_components.py` 出选型：

- **yes**：用户明确需要，或产品闭环里必然包含。例如碰到照片、身份、支付、替用户发消息这类隐私或敏感数据，`destructive_ops` 就是 yes。
- **later**：用户原话里有「以后 / 二期 / 将来再做」这类依据。没有原话依据不要写 later。
- **no**：产品闭环已经说清楚，而这个特征不在闭环里、也与产品形态明显无关。
- **unknown**：信息不足、确实无法判断时才用。不要因为「用户没逐字提到」就写 unknown：一个单人、单次、同步的闭环已经写明时，定时调度、多 Agent 团队、外部插件生态这类特征应判 no。

| 特征 id | 问题 | 决定的组件 |
|---|---|---|
| `destructive_ops` | 是否涉及破坏性或敏感操作（删除、写入外部系统、支付、发送消息、隐私数据）？ | s03 权限系统 |
| `audit_needed` | 是否需要审计、拦截、埋点、合规记录？ | s04 钩子系统 |
| `multi_step` | 单次交付是否需要先列计划再逐步推进并跟踪进度（多轮、可中断、要汇报进展）？固定顺序调用几个工具不算。 | s05 任务规划 |
| `context_heavy` | 是否会出现上下文爆炸的子任务，或可并行的探索型子任务？ | s06 子 Agent |
| `large_knowledge` | 领域知识库是否庞大、需要按需加载？ | s07 技能加载 |
| `long_sessions` | 会话是否很长、工具输出或日志量是否很大？ | s08 上下文压缩 |
| `cross_session_memory` | 是否需要跨会话记住用户偏好、决策、历史？ | s09 记忆系统 |
| `persistent_goals` | 目标是否需要持久化、支持断点续跑？ | s10 任务系统 |
| `slow_operations` | 是否有耗时几分钟以上的慢操作需要不阻塞主流程？ | s11 后台任务 |
| `scheduled` | 是否需要定时自动触发？ | s12 定时调度 |
| `parallel_isolated` | 是否需要多任务并行且各自隔离工作区（多 Agent 团队）？ | s13 Agent 团队 |
| `external_ecosystem` | 是否需要接入外部工具生态（MCP、第三方插件）？ | s14 MCP 插件 |
| `fixed_orchestration` | 输入是否把流程写成固定的阶段序列（如「上传→翻译→标注→入库」）且各阶段无需模型临场决策？只描述产品体验、或流程里有模型判断分支的不算。 | s16 工作流运行时 |
| `auto_completion` | 是否需要自动判断「何时算完成」（独立评估器）？ | s17 目标闭环 |

## 4. 17 个组件

s01、s02 恒选。s15 不靠特征：第一版选了 3 个以上可选组件就必选（脚本自动算）。原则是**宁可少选**：对每个组件问「没有它产品会怎样」，答不上就不选。

| 组件 | 领域 | 一句话 | 什么时候需要 | 做到生产级的要点 |
|---|---|---|---|---|
| s01 Agent Loop | 行动域 | 最小可运行闭环 | 一切基础：循环 + 工具 | 重试、超时、token 上限、stop_reason 完整处理 |
| s02 工具系统 | 行动域 | 循环不变，工具可增 | 需要调用外部系统/API/数据源 | JSON schema 严格、参数校验、错误回传格式统一 |
| s03 权限系统 | 约束域 | 先划边界，再给自由 | 涉及破坏性/敏感操作 | 白名单/黑名单、破坏性操作二次确认、审计日志、默认拒绝 |
| s04 钩子系统 | 约束域 | 挂循环上，不写循环里 | 需要审计、拦截、埋点 | PreToolUse 可阻断、PostToolUse 可观察、异常不影响主循环 |
| s05 任务规划 | 认知域 | 先计划后执行 | 多步骤、需跟踪进度 | 计划持久化、状态流转、进度可查询 |
| s06 子 Agent | 上下文域 | 全新消息列表，隔离噪声 | 上下文会爆、任务可并行 | 独立消息列表、最终文本回传、超时回收 |
| s07 技能加载 | 认知域 | 用到时再加载 | 领域知识库庞大 | 目录先行、按需展开、版本管理 |
| s08 上下文压缩 | 上下文域 | 长上下文腾空间 | 长会话、日志量大 | 分层压缩、先裁工具结果再摘要历史、保留权威指令 |
| s09 记忆系统 | 认知域 | 记住该记的，忘掉该忘的 | 需跨会话记住偏好/决策 | 筛选→提取→整合三子系统、持久化 + 检索、冲突时用户指令优先 |
| s10 任务系统 | 协作域 | 大目标拆小任务，持久化 | 目标需持久化、断点续跑 | 文件持久化、依赖图、原子状态变更、并发锁 |
| s11 后台任务 | 协作域 | 慢操作丢后台 | 有慢操作需不阻塞 | 线程池、完成通知注入、超时与清理 |
| s12 定时调度 | 协作域 | 到点自动触发 | 需定时自治触发 | 持久化调度、幂等、会话级作用域 |
| s13 Agent 团队 | 协作域 | 队友分工协作 | 多任务并行、需隔离工作区 | 原子认领、任务绑定 worktree、异步邮箱、类型化协议、关停流程 |
| s14 MCP 插件 | 行动域 | 外部工具接入同一工具池 | 需接入外部工具生态 | 工具发现、mcp__server__tool 命名空间、连接失败降级 |
| s15 集成 Harness | 编排域 | 多机制归一循环 | 上述机制需协同（选了 3 个以上可选组件） | 单一循环、动态重建系统提示词、共享客户端、跨模块状态协调 |
| s16 工作流运行时 | 编排域 | 编排形状固定就写进代码 | 编排形态固定 | 脚本拥有编排、生命周期事件、journal 断点续跑 |
| s17 目标闭环 | 认知域 | 目标决定循环何时停止 | 需自动判断「何时算完成」 | 独立评估器、目标不可能/失败/超限时交还控制权 |

## 5. 七层架构

方案里的分层架构图和工具清单的「归属层」都用这七层，编号不要另起一套：

| 层 | 回答的问题 | 包含什么 |
|---|---|---|
| ① 交互层 | 谁在用、怎么用？ | CLI / Web / App / API；同步或异步；人机比 |
| ② 产品层 | 产品外壳是什么？ | 会话管理、请求路由、账户、业务逻辑 |
| ③ Agent 编排层 | Harness 如何运转？ | loop、工具分发、hooks、权限、记忆、任务、技能、压缩、子 agent / 团队、目标闭环 |
| ④ 模型层 | 智能从哪来？ | 主模型、辅助模型、路由、fallback、成本 |
| ⑤ 能力集成层 | 如何触达外部世界？ | 内部工具、MCP server、知识库、第三方 API |
| ⑥ 数据层 | 什么需要持久化？ | 记忆、任务、会话历史、轨迹数据、日志指标 |
| ⑦ 基础设施层 | 如何部署运行？ | 单进程 / 服务 / 团队、沙箱、队列、调度、监控 |

调外部系统、知识库、第三方 API 的工具归 ⑤；读写需要持久化的数据的工具归 ⑥。

## 6. 生产级验收标准

方案要说明每一条怎么做到，否则交付的只是 demo：

- **可运行**：一条命令能起，配置与密钥外置（.env / config）
- **可容错**：工具失败、模型幻觉、超时、越权都有明确降级路径
- **可观测**：有日志、有指标、有轨迹数据
- **可测试**：核心循环与工具分派有单测，权限与安全有边界测试
- **可部署**：有明确的部署形态（单进程 / 服务 / 团队）与启动文档
- **可度量**：有对齐 PRD 的成功指标，并能采集

## 7. 手工选型规则

不能运行 `scripts/select_components.py` 时，按下面的规则手工推导。这就是脚本里的全部规则，照做结果和脚本一字不差。

1. **s01 Agent Loop、s02 工具系统**：一律「必选」，理由写组件的「什么时候需要」，后面加「（一切基础，恒选）」。
2. **s03～s14、s16、s17**：每个组件看第 3 节里决定它的那个特征（表里「决定的组件」一列）：

   | 特征判断 | 选否 | 理由 |
   |---|---|---|
   | `yes` | 必选 | 你写的依据；没写依据就用组件的「什么时候需要」 |
   | `later` | 二期 | 同上 |
   | `unknown`、没判断、或写了这四个值以外的值 | 待确认 | 「输入未说明：」加上这个特征的问题原文 |
   | `no` | 放弃 | 你写的依据；没写就用「输入表明不需要：」加上组件的「什么时候需要」 |

3. **s15 集成 Harness**：数一数 s03～s14、s16、s17 里的结果：
   - 「必选」有 3 个或以上 → 必选，理由写「第一版已选 N 个可选组件（编号用英文逗号加空格隔开），需归一到单一循环」；
   - 否则，「必选」加「二期」有 3 个或以上 → 二期，理由写「含二期共 N 个可选组件，二期集成时需要」；
   - 否则 → 放弃，理由写「可选组件不足 3 个，直接在 loop 里挂接即可」。
4. 按 s01 到 s17 的顺序排成表，表头是 `| 组件 | 选否 | 理由 |`，选否一列写 `✅ 必选`、`⏸ 二期`、`❓ 待确认`、`❌ 放弃`。
